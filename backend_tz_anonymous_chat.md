# ТЗ: backend для защищённого 1:1 чата

## 1. Цель проекта
Создать production-ready backend для Android-приложения защищённого чата 1:1 со следующими свойствами:
- обмен текстовыми сообщениями и файлами;
- несколько отдельных чатов между одной и той же парой пользователей;
- end-to-end encryption на клиенте;
- опциональное дополнительное шифрование по общему секрету пользователей;
- хранение на сервере только зашифрованного содержимого;
- удаление сообщений/файлов по правилам чата, сообщения или пользователя;
- поддержка удаления сообщений у себя, у всех, а также очистки диалога у обоих;
- push-уведомления без текста сообщения;
- серверная история с ограниченным сроком хранения, по умолчанию до 60 дней;
- строгая модель 1:1 без групповых чатов.

## 3. Общие функциональные требования

### 3.1 Пользователи
- У пользователя есть уникальный `nickname`.
- Вход выполняется по `nickname + password`.
- Пароль хранится только в виде хеша `Argon2id`.
- Email указывается опционально.
- Если включена email-защита, после успешной проверки логина/пароля сервер отправляет 6-значный код на email.
- Без корректного email-кода вход не завершается.

### 3.2 Устройства
- Регистрация устройства обязательна.
- На старте поддерживается один активный девайс на аккаунт.
- Устройство хранит криптографические ключи локально.
- При регистрации устройство передаёт на сервер:
  - public identity key;
  - signed prekey;
  - signed prekey signature;
  - batch one-time prekeys;
  - FCM token;
  - device UUID и технические сведения.

### 3.3 Чаты
- Только 1:1 чаты.
- Между двумя одними и теми же пользователями может существовать несколько независимых `conversation_id`.
- Каждый чат имеет собственные настройки:
  - обычный режим;
  - режим дополнительной защиты по shared secret;
  - срок хранения;
  - автоудаление после прочтения.

### 3.4 Сообщения
- Сервер не хранит сообщения в открытом виде.
- Сообщения шифруются только на клиенте отправителя.
- Расшифровка выполняется только на клиенте получателя.
- Сервер хранит ciphertext и метаданные доставки/синхронизации.
- Для каждого сообщения должен существовать уникальный `message_id`.
- В маршрутизации обязательно участвуют:
  - `chat_id` / `conversation_id`;
  - `user_id`;
  - `device_id`;
  - `sender_device_id`;
  - `recipient_device_id`;
  - `message_id`.

### 3.5 Файлы
- Файлы шифруются на клиенте до загрузки.
- В MinIO/S3 хранится только зашифрованный blob.
- Метаданные файла хранятся в PostgreSQL.
- Поддерживаются:
  - загрузка одного файла;
  - массовая загрузка до 20 файлов за одну операцию.
- После удаления сообщения у всех связанный файл тоже должен быть удалён из объектного хранилища.

## 4. Криптографическая модель

### 4.1 Базовая модель
Используется модель, близкая к Signal Protocol:
- у каждого устройства есть `identity key pair`;
- `signed prekey`;
- набор `one-time prekeys`.

### 4.2 Начало диалога
1. Клиент отправителя запрашивает у сервера публичный key bundle получателя.
2. Сервер отдаёт публичные ключи целевого устройства.
3. На клиенте строится сессионный ключ.
4. Сообщение шифруется локально.
5. На сервер отправляется только encrypted envelope.

### 4.3 Дополнительное шифрование по общему секрету
Опциональный режим `shared_secret`:
- два пользователя заранее договариваются о секретной фразе вне системы;
- фраза не отправляется на сервер и не хранится на сервере;
- из фразы на клиенте выводится ключ через `Argon2id`;
- затем полезная нагрузка шифруется локально;
- результат помещается внутрь обычного Signal-like envelope.

Схема:

```text
plaintext
 -> optional shared-secret encryption
 -> signal/session encryption
 -> server
```

## 5. Модель хранения данных

### 5.1 Сервер хранит
- ciphertext сообщений;
- encrypted file blobs;
- технические метаданные;
- события синхронизации;
- статусы доставки и прочтения;
- данные для push;
- публичные ключи устройств.

### 5.2 Сервер не хранит
- plaintext сообщений;
- plaintext файлов;
- shared secret пользователей;
- приватные ключи устройств;
- расшифрованные вложения.

## 6. Сроки хранения
- Базовый срок хранения сообщения/файла: до 60 дней.
- Срок может быть уменьшен:
  - настройками чата;
  - настройками конкретного сообщения;
  - автоудалением после прочтения.
- Управление удалением делает Celery.
- Redis TTL не используется как основной механизм хранения сообщений.

## 7. Статусы сообщений

### Пользовательские статусы
- Отправлено
- Доставлено
- Прочитано
- Удалено
- Истекло

### Серверные статусы
- `server_received`
- `device_delivered`
- `read`
- `hidden_for_user`
- `deleted_global`
- `expired`
- `purged`

## 8. Режимы удаления

### 8.1 Удалить только у себя
- Пользователь скрывает сообщение только в своей выдаче.
- На сервере создаётся запись `message_visibility_override`.
- Для второго участника сообщение продолжает существовать.

### 8.2 Удалить у всех
- Только автор сообщения может удалить его у обоих участников.
- Сервер помечает сообщение как глобально удалённое.
- Создаётся событие `message_deleted_global`.
- При наличии файлов они тоже удаляются.

### 8.3 Очистить диалог у обоих
- Отдельная destructive-операция.
- Подтверждение второй стороны не требуется.
- Все сообщения данного `conversation_id` глобально удаляются.
- Все вложения данного чата удаляются.
- Чат как контейнер может остаться существующим для новой переписки.

## 9. Удаление аккаунта при неудачных входах

### Политика блокировок
- После 3–5 неудачных попыток: блок на 3 часа.
- После следующей серии: блок на 6 часов.
- После следующей серии: блок на 24 часа.
- После следующей серии: инициируется уничтожение аккаунта.

### Поведение при уничтожении аккаунта
- Все `conversation`, где участвует пользователь, помечаются как `purged`.
- Все сообщения в этих чатах глобально удаляются.
- Все файлы удаляются из MinIO/S3.
- Все ключи, токены, сессии и связанные данные удаляются.
- Вторым участникам отправляется service event:
  - `Чат недоступен`.
- Причина не раскрывается.

## 10. Push-уведомления
- Используется Firebase Cloud Messaging (FCM).
- Push не содержит текста сообщения и не содержит содержимого файла.
- Допустимые варианты:
  - `У вас новое сообщение`
  - `У вас N непрочитанных сообщений`
- Push инициируется сервером после записи сообщения и анализа статуса online/offline.

## 11. Online / Offline
- Статус online определяется наличием активного WebSocket и heartbeat.
- Быстрый статус хранится в Redis.
- Долгосрочный `last_seen_at` хранится в PostgreSQL.
- Для нескольких инстансов backend используется Redis pub/sub.

## 12. Event-driven синхронизация
История и изменения синхронизируются через события.
Примеры событий:
- `message_created`
- `message_deleted_global`
- `message_hidden_for_user`
- `conversation_cleared_local`
- `conversation_cleared_global`
- `message_delivered`
- `message_read`
- `file_deleted`
- `participant_key_changed`
- `chat_purged`

## 14. Нефункциональные требования

### Безопасность
- только HTTPS / WSS;
- HSTS;
- secure cookies / bearer tokens;
- ротация refresh token;
- логирование без утечки ciphertext, токенов, email-кодов и ключей;
- локальное шифрование чувствительных данных на Android;
- отображение fingerprint/safety code пользователю.

### Производительность
- горизонтальное масштабирование API;
- Redis как слой realtime-маршрутизации;
- RabbitMQ как надёжный брокер задач;
- партиционирование крупных таблиц PostgreSQL по времени;
- индексация по `conversation_id`, `created_at`, `event_id`, `recipient_user_id`.

### Надёжность
- idempotency для отправки сообщений и destructive-операций;
- повторные попытки push и фоновых задач;
- дедупликация событий;
- транзакционность записи сообщения и событий.

## 15. Предлагаемые фоновые задачи Celery
- удаление сообщений по `expires_at`;
- удаление вложений из MinIO;
- пересчёт unread counters;
- рассылка push-уведомлений;
- очистка старых email-кодов;
- очистка старых prekeys;
- purge аккаунта;
- cleanup dangling upload sessions;
- пересчёт read-based expiration.

## 16. Правила UX и продуктовые ограничения
- Только официальный клиент гарантирует корректную обработку delete events.
- Удаление у обоих означает удаление на сервере и в официальном клиенте, но не может криптографически гарантировать уничтожение уже вручную сохранённого контента на скомпрометированном устройстве.
- Никнейм уникален, но маршрутизация сообщений выполняется не по никнейму, а по `conversation_id + user_id + device_id`.

## 17. Результат проекта
В результате должен быть реализован backend production-уровня для безопасного 1:1 чата с E2EE, optional shared secret, серверной синхронизацией, файловыми вложениями, event-driven моделью удаления и полной поддержкой Android-клиента.
