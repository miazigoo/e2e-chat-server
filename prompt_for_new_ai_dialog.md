# Промт для нового диалога с ИИ

Ниже промт, который можно использовать в новом диалоге, чтобы быстро восстановить контекст проекта.

---

Мне нужно продолжить проектирование backend для защищённого Android-чата 1:1. Ниже зафиксирована актуальная архитектура, от которой нельзя отходить без явного обсуждения.

## Общая цель
Нужен production-ready backend для анонимного/приватного чата 1:1 без групп. Приложение Android на Kotlin. Сервер — FastAPI в Docker.

## Уже принятые архитектурные решения

### Backend stack
- FastAPI
- PostgreSQL
- Redis
- RabbitMQ
- Celery
- MinIO / S3-compatible storage
- FCM для Android push
- Nginx/Caddy для HTTPS

### Криптография
Используем модель, близкую к Signal Protocol:
- у каждого устройства есть identity key pair;
- signed prekey;
- набор one-time prekeys;
- при начале диалога клиент отправителя запрашивает у сервера публичные ключи получателя;
- сеансовый ключ строится на клиенте;
- сообщение шифруется только на устройстве отправителя;
- расшифровка только на устройстве получателя.

### Дополнительное шифрование
Есть optional режим `shared secret`.
Схема строго такая:

```text
plaintext
 -> optional shared-secret encryption
 -> signal/session encryption
 -> server
```

Shared secret:
- не хранится на сервере;
- хранится только локально у пользователей;
- используется как дополнительный слой содержимого.

### Модель чатов
- только 1:1;
- между одной и той же парой пользователей может быть несколько разных чатов;
- каждый чат имеет отдельный `conversation_id`;
- один чат может быть обычным, другой — с shared secret.

### Устройство
- один активный девайс на аккаунт.

### Идентификаторы
Для маршрутизации и безопасности обязательно использовать:
- `user_id`
- `device_id`
- `conversation_id`
- `sender_device_id`
- `recipient_device_id`
- `message_id`

Не маршрутизировать сообщения только по nickname.

### Хранение
- сообщения хранятся в PostgreSQL;
- только в зашифрованном виде;
- файлы хранятся в MinIO/S3;
- файлы шифруются на клиенте до загрузки;
- на сервере нет plaintext сообщений и файлов.

### Срок хранения
- по умолчанию до 60 дней;
- может быть меньше по настройкам чата или сообщения;
- может быть автоудаление через N часов после прочтения;
- удалением управляет Celery.

### Удаление сообщений
Три режима:
1. удалить только у себя — через `message_visibility_override`;
2. удалить у всех — только автором своих сообщений;
3. очистить диалог у обоих — отдельная destructive operation без подтверждения второй стороны.

### Очистка при удалении аккаунта
Если аккаунт уничтожается:
- все conversation, где участвовал пользователь, помечаются как `purged`;
- все сообщения в этих чатах глобально удаляются;
- все файлы удаляются из storage;
- вторым участникам приходит service event: `чат недоступен` без деталей.

### Авторизация
- логин по `nickname + password`;
- пароль хранится как Argon2id hash;
- optional email 2FA: если включено, на email уходит 6-значный код после правильного логина/пароля.

### Политика неудачных входов
- несколько неудачных попыток -> бан на 3 часа;
- затем 6 часов;
- затем 24 часа;
- затем при следующей серии неправильных попыток аккаунт уничтожается вместе с сообщениями, чатами и файлами.

### Push
- только через FCM;
- push без текста сообщения;
- варианты: `У вас новое сообщение` или `У вас N непрочитанных сообщений`.

### Online/Offline
- нужен статус online/offline;
- Redis используется для presence, websocket routing, pub/sub, unread counters, locks, short-lived auth state.

### Синхронизация
Нужна event-driven модель с таблицей `conversation_events`.
События включают как минимум:
- `message_created`
- `message_deleted_global`
- `message_hidden_for_user`
- `conversation_cleared_local`
- `conversation_cleared_global`
- `message_delivered`
- `message_read`
- `file_deleted`
- `participant_key_changed`
- `chat_purged`

### Безопасность
- только HTTPS/WSS;
- без HTTP;
- fingerprint/safety code пользователей нужно показывать в клиенте;
- приватные ключи только на устройстве.

## Что важно учитывать в дальнейших ответах
- Не предлагать Telegram-подобную соцсеть, группы или публичные каналы.
- Не упрощать до MVP; проектируется сразу production-архитектура.
- Не убирать Redis, если он нужен для полноценного продакшина.
- Не предлагать PGP как основную схему чата; основа — Signal-like.
- Источник истины для истории сообщений — сервер, но в зашифрованном виде.
- Клиентский кэш не считается основной историей.
